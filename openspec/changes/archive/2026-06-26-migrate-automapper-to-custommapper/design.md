## Context

The Reactivities backend uses AutoMapper with two convention-based profiles defined in `Application/Core/Mappings/MappingProfiles.cs`:

- `CreateActivityRequest → Activity` — maps 8 shared properties by name; `Activity.Id` is excluded (generated by the entity) and `Activity.IsCancelled` is excluded (defaults to `false`).
- `Activity → Activity` — used exclusively in `UpdateActivity.Handler` to copy all writable properties from the incoming `Activity` (from the request body) onto the EF-tracked entity, preserving the tracked entity's identity.

`IMapper` is injected into two MediatR handlers via primary constructor parameters. No other code in the solution references AutoMapper.

**Current state summary:**
- 1 profile class, 2 mapping rules, 2 call sites
- Both mappings rely entirely on AutoMapper's name-matching convention; no `ForMember`, `Ignore`, or custom resolvers

## Goals / Non-Goals

**Goals:**
- Remove the `AutoMapper` NuGet package from `Application.csproj`
- Provide an explicit, readable mapper that preserves identical mapping semantics
- Keep the mapper registered in DI so handlers remain testable via interface substitution

**Non-Goals:**
- No generic or reflection-based mapping (this is not a framework replacement)
- No changes to `Activity`, `CreateActivityRequest`, or any API contract
- No frontend changes
- No new mapping pairs beyond the two that exist today

## Decisions

### 1. Interface `IActivityMapper` over a static class

**Decision**: Define `IActivityMapper` (interface) + `ActivityMapper` (implementation), registered via `AddScoped<IActivityMapper, ActivityMapper>()`.

**Rationale**: MediatR handlers already follow constructor injection. An interface keeps the handlers mockable in tests without changing their DI pattern. A static class would require refactoring call sites if tests need substitution.

**Alternative considered**: Static helper class `ActivityMapper.ToActivity(...)` — simpler to write but cannot be mocked; breaks the existing testability posture.

### 2. Placement in `Application/Core/` (not `Domain/`)

**Decision**: Place both `IActivityMapper` and `ActivityMapper` in `Application/Core/`.

**Rationale**: Mapping between a request DTO and a domain entity is application-layer logic per Clean Architecture. The `Domain` project has no dependency on `Application`, so placing the interface there would create an inverted dependency.

### 3. Two methods on the interface

```csharp
Activity ToActivity(CreateActivityRequest request);
void UpdateActivity(Activity source, Activity destination);
```

**Rationale**: Names mirror the two existing AutoMapper call patterns. `UpdateActivity` mutates `destination` in-place (same semantics as `mapper.Map(source, destination)`), which is required because `UpdateActivity.Handler` uses the EF-tracked entity as the destination.

### 4. `AddScoped` registration

**Decision**: Register as `AddScoped<IActivityMapper, ActivityMapper>()`.

**Rationale**: `ActivityMapper` is stateless; `AddSingleton` would also work. `AddScoped` is the conventional default for application services and makes no practical difference here.

## Risks / Trade-offs

**Property drift** → Mitigation: Unlike AutoMapper's convention binding, the custom mapper will not automatically pick up new properties added to `Activity` or `CreateActivityRequest`. When either type gains a new field, the implementer must also update `ActivityMapper`. This is a compile-time-silent risk. Mitigate by adding a compiler-visible property count assertion or a unit test that enumerates public settable properties.

**`UpdateActivity` semantics — `Id` preservation** → Mitigation: The `Activity → Activity` update MUST NOT overwrite `destination.Id`. The source `Activity` arrives from the request body; its `Id` is the route parameter, but the tracked entity's `Id` is the authoritative value. The implementation must explicitly skip `Id` (and `IsCancelled` is intentionally carried over in the update path).

## Migration Plan

1. Add `IActivityMapper.cs` and `ActivityMapper.cs` to `Application/Core/`.
2. Update `Program.cs`: remove `AddAutoMapper(...)`, add `AddScoped<IActivityMapper, ActivityMapper>()`.
3. Update `CreateActivity.Handler` and `UpdateActivity.Handler`.
4. Delete `Application/Core/Mappings/MappingProfiles.cs` (directory can be removed if empty).
5. Remove `<PackageReference Include="AutoMapper" .../>` from `Application/Application.csproj`.
6. Run `dotnet build` — verify zero errors.

**Rollback**: Git revert. No database migrations or data changes are involved.
